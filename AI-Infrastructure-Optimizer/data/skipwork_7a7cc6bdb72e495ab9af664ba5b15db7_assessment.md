## 판정

Baseline은 기존 Hybrid의 산술 도구/비산술1.5B 해결 뒤 전수 재검증을 추가한 **연구용 대조군**이다. 기존 최선의 Hybrid를 직접 이겼다는 결과가 아니다. 단순 해결만으로 이미 101~102/150(67.33~68.00%)이 맞았는데, 전수 검증이 87/150로 악화시켰다. 이 primary 지표는 실제 관측 응답의 사후 채점이며, 이전 Hybrid의 새 실행 시간이나 별도 경쟁 방식 측정값으로 쓰지 않는다.

## 가설별 해석

1. **안전 산술 Early Exit(기존 도구 대조 실험):** 산술 검증30회를 생략해 산술 정답18→30개. `38 * 67`의 도구 정답2546을 검증 모델이2286으로 바꾸는 등 불필요한 재생성이 정확도를 해쳤다. 총 호출270→240, 생성시간6.035→4.747초, CPU19.59→15.61초로 줄었지만 실제 처리시간27.660→29.223초, 평균 지연439.51→473.26ms로 늘었다. 단일 실행 벽시계 속도 개선은 입증되지 않았다. 모델 연산 대리 지표와 사용자 지연을 구분해야 한다.

2. **새 가설: 검증의 예상 순이득 기반 Selective Verification.** 보정에서 검증이 개선하지 못한 쉬운 유형은 생략하면 검증 호출을 줄일 수 있다고 가정했다. 도구30+지식30의 검증을 사전 생략해 총 호출270→210(-22.22%), 입력 토큰27532→22421(-18.57%), 출력639→428(-33.02%), 생성6.035→3.915초, CPU19.59→13.84초, 처리27.660→24.370초(-11.89%)였다. 그러나 보정 지식은1차20/20 정답, 검증이0건 개선/2건 악화한 반면 새 수도 문제는1차26/30만 형식 충족했다. 필요한 형식 복구3건도 생략해 답변149→146, 정답은 Early Exit100→97로 감소했다. 점추정·유형 일반화가 실패했다. 정확도만 Baseline보다 올랐다는 이유로 성공이라 할 수 없다.

3. **새 가설: 출력 예산 상한(Budget Cap).** 객관식 해결 출력 상한64→8토큰으로 줄여 출력 생성 작업량을 줄일 수 있다고 가정했다. 실제 총 입력/출력 토큰은 Baseline과 완전히 같았고 모든 호출 종료는stop이었다. 상한이 실제 출력을 줄이지 못했다. 호출270, 생성6.172초, CPU19.77초, 처리31.687초로 절감 근거가 없다. +1문항 정답 차이는 아래 동일 프롬프트 응답 차이와 얽혀 예산 효과로 주장할 수 없다.

4. **새 가설: 사전 묶음 검증(Batch Verify).** 유형/길이만으로 최대4개를 함께 검증하면 고정 호출 오버헤드를 줄일 수 있다고 가정했다. 호출270→160(-40.74%)이지만 출력639→2099(+228.48%), 생성6.035→31.839초, CPU19.59→56.52초, 처리27.660→59.741초(+115.98%), 평균지연439.51→1538.76ms로 악화했다. 40개 응답 모두 JSON을 Markdown 코드펜스로 감싸 엄격한JSON계약을 위반했다. 모든150개 검증이 채택되지 않고 1차 답을 보존했으므로 정답101개를 성공적인 묶음 검증 효과로 주장할 수 없다.

## 정확도 손실·형식 오류·불필요 검증

Baseline은 검증13건 개선,28건 악화,74건 정답 유지,35건 여전히 오답/미해결이었다. Selective는11건 개선,15건 악화,30건 정답 유지,34건 여전히 실패,60건 생략이었다. 정답 유지 사례는 사후 결과상 중복이며 사전에 정답을 알고 생략한 것이 아니다. 어려운 논리는 보수적 규칙에 따라 검증을 유지했지만12건 악화했다. 예: 키 순서에서 정답D를B로, `audit4.split` 결과 정답A를Error인D로 바꿨다. 같은 모델을 다시 호출하는 것이 신뢰도 보증이 되지 않았다.

Baseline 대비 문항별 손익은 Early Exit 정답→오답0/오답→정답13, Selective3/13, Budget Cap0/1, Batch13/27이다. 총점만으로 문항별 손실을 가리지 않았다.

출력 계약은 단일 문자 또는 정수다. Selective의 미답변4건은 폴란드/노르웨이/스웨덴/핀란드 수도 문제에서 `A) Warsaw`, `A) Oslo`, `A)`, `A) Helsinki`처럼 옵션 표기를 붙인 응답이었다. 내용 오답으로 단정할 수 없는 **형식 오류**다. Baseline/Early Exit는 재검증으로 이 중3개를 복구했다. 실행 중 이를 사후 구제하거나 공식 점수를 덮어쓰지 않았다.

별도 사후 진단은 정답을 입력받지 않는 안전한 옵션 표기/정확한 옵션 본문 매칭으로 해석 가능한 최종 답만 확인했다. 아래 수치는 공식 성능이 아닌 **출력 형식 진단**이며 시간/호출 절감 재실험 결과가 아니다.
